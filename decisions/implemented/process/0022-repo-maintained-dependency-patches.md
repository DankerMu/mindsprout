# Maintain exact-version JavaScript dependency patches with pnpm

## Problem

`@stryker-mutator/vitest-runner@10.1.1` logs the resolved Vitest config at debug level with `JSON.stringify`. Vitest 5's resolved config is circular (`resolvedProjects[0].viteConfig.test`), so debug-level mutation runs fail in `VitestTestRunner.init` before the initial test run (#118). The upstream fix, stryker-js#6261, is open and unreleased. 10.1.1 is the latest release. The repository had no mechanism for shipping a reviewed fix to published JavaScript, and Renovate owns version changes.

## Decision

The owner approved a repository-maintained patch on 2026-11-11. JavaScript-only fixes to a published dependency's shipped files use pnpm `patchedDependencies` in `package.json`:

- **Location and pin.** One file per package at `patches/<scope>__<name>@<exact-version>.patch`, generated by `pnpm patch` / `pnpm patch-commit`. The key names the exact installed version, never a range. pnpm records the patch hash in `pnpm-lock.yaml`. The lockfile changes only by that metadata.
- **Minimal and upstream-shaped.** The patch edits shipped `dist/` files only and mirrors the upstream candidate, so removing it is a clean revert. The first patch replaces line 153 of `dist/src/vitest-test-runner.js` with upstream's `this.log.debug('vitest final config: %O', this.ctx.config)`. Stryker core formats that call with `util.format` in the worker before transport. The second patch wraps the final `String(error)` of `errorToString` in `@stryker-mutator/util@10.1.1` `dist/src/errors.js` in the try/catch of the upstream candidate stryker-js#6226 (#119).
- **Loud failure, measured with pnpm 10.28.** A frozen install whose patch key or patch bytes disagree with the lockfile fails with `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`. Re-resolving with a key that matches no installed version fails with `ERR_PNPM_UNUSED_PATCH`. A patch whose context no longer matches fails with `ERR_PNPM_PATCH_FAILED`. The repository has no `allowUnusedPatches` or `ignorePatchFailures` setting, and none may be added.
- **Regression at the installed seam.** `pnpm test:stryker-patch` (CI layer 4, after a frozen install) imports the runner from `node_modules` and asserts that it resolves to the pnpm entry carrying `patch_hash`. It then covers the circular debug config, the unchanged non-debug path and error propagation. For the util patch it asserts that the runner, Stryker core and the instrumenter all resolve the patched util entry, then covers unstringifiable inputs, the unchanged output of every input `String` can convert, and the error results of `dryRun` and `mutantRun`.

[Dependency patch instructions](../../../docs/engineering/dependency-patches.md) own the add, update and remove commands. This decision does not supersede [decision 0021](../bug-fix/0021-native-hmr-registration-maintenance.md). It adds a parallel mechanism for JavaScript dist fixes. Native binaries keep their source-pinned rebuild, exact-version overrides and postinstall guard.

## Alternatives considered

- **Wait for an upstream release:** leaves debug-level mutation diagnosis unusable for an unknown period. Running at info level is a workaround, not a fix.
- **`pnpm.overrides` to a fork or tarball (the 0021 mechanism):** needs a published artifact, provenance and integrity pins for a one-line JavaScript change. It also hides the delta inside a tarball instead of a reviewable diff.
- **A postinstall script that rewrites `node_modules`:** bypasses pnpm's content-addressed install. It can silently stop matching, and it binds no hash in the lockfile.
- **Wrap the runner or swallow the logging error:** changes runner behavior and hides future init failures. That violates the invariant that debug logging never changes initialization.
- **Log a hand-picked subset of config fields (the issue's first suggestion):** diverges from upstream, so the patch cannot be dropped by a clean revert.
- **Circular-safe JSON serializer:** prints more detail but requires rules for non-JSON values, and it also diverges from upstream.

## Consequences

- `%O` uses `util.inspect` at its default depth of 2. Deeper values print as `[Object]`; in the measured repository run that already truncates `resolvedProjects[0].viteConfig` before the cycle, and `util.inspect` marks any cycle it reaches as `[Circular *n]`. Top-level keys such as `root`, `include` and `resolvedProjects` remain, which matches upstream's trade-off. Deeper inspection needs a debugger, not a deeper log.
- A Renovate update of a patched package cannot land unchanged. In the measured case, the specifier moved to another published version and the `@10.1.1` key stayed. Lockfile regeneration failed with `ERR_PNPM_UNUSED_PATCH` and wrote no lockfile, and the frozen install against the stale lockfile failed with `ERR_PNPM_OUTDATED_LOCKFILE`. Renovate itself was not exercised. The updater must remove the patch if the new release contains the fix, or regenerate it for the new version and re-run its regression and evidence. A patch is never carried silently across versions.
- Removal condition: a released version contains the fix. In that Renovate PR, remove the patch file and its `patchedDependencies` entry, [regenerate the lockfile](../../../docs/engineering/dependency-patches.md#regenerate-the-lockfile), then delete the regression or re-target it at the stock file. Rollback is the same revert of patch, entry and lockfile; no user data is affected.
- Every patch is a review obligation. Its diff, its upstream reference and its removal condition must stay current in the instructions linked above.
