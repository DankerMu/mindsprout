# Spec Delta

## Purpose

Turn a topic into a stream of validated TreeOps through one provider-neutral port, so every model transport (Claude direct, OpenAI-compatible, mock) yields the same safe op stream for the map.

## ADDED Requirements

### Requirement: One provider is configured from server environment

The server SHALL select at most one platform provider from `AI_PROVIDER` (`anthropic`, `openai-compatible` or `mock`) and its model from `AI_MODEL`. An empty value SHALL count as unset for every AI variable. Provider keys and base URLs SHALL exist only in server environment, never in the client bundle, logs or database. No model id SHALL be built into the code.

#### Scenario: AI not configured

- **WHEN** `AI_PROVIDER` is unset or empty
- **THEN** environment loading succeeds and generation reports `ai-unavailable` without calling any provider

#### Scenario: Example environment loads

- **WHEN** the environment is a verbatim copy of `.env.example`
- **THEN** environment loading succeeds with AI unconfigured

#### Scenario: Partially configured provider fails at load

- **WHEN** `AI_PROVIDER=openai-compatible` is set and `OPENAI_API_KEY`, `OPENAI_BASE_URL` or `AI_MODEL` is missing or empty
- **THEN** environment loading throws an error naming the missing variable

#### Scenario: Claude provider configuration

- **WHEN** `AI_PROVIDER=anthropic` is set with `ANTHROPIC_API_KEY` and `AI_MODEL`
- **THEN** environment loading succeeds, and `ANTHROPIC_BASE_URL` is used only when it is set

#### Scenario: Mock refused in production

- **WHEN** `AI_PROVIDER=mock` and `NODE_ENV=production`
- **THEN** environment loading throws

### Requirement: Generation emits only validated add_children ops with fresh ids

For a topic and the map's primary root id, a provider SHALL emit only `add_children` TreeOps without an index. Each op SHALL target the primary root or a node emitted earlier in the same attempt. Each op SHALL carry at least one child, every child with non-empty text and an id freshly generated by the server, never an id chosen by the model. Every emitted op SHALL pass the TreeOp schema. Invalid model output SHALL be rejected, never repaired.

#### Scenario: Model temporary ids are replaced

- **WHEN** the model calls the tool with parent `root` and children `a` and `b`, then with parent `a`
- **THEN** the first op targets the primary root id, the second op targets the server id that replaced `a`, and no emitted id equals `a` or `b`

#### Scenario: Unknown parent is invalid output

- **WHEN** the model references a parent id that it never introduced
- **THEN** the call is rejected as invalid output

#### Scenario: Duplicate temporary id is invalid output

- **WHEN** the model reuses a temporary id it already introduced, whether that id was emitted or dropped
- **THEN** the call is rejected as invalid output

#### Scenario: Malformed tool input is invalid output

- **WHEN** a tool input has an unknown field, an empty children list, empty text or unparseable JSON
- **THEN** it is rejected as invalid output

#### Scenario: No tool call is invalid output

- **WHEN** a model attempt ends normally without any tool call
- **THEN** the attempt is treated as invalid output

### Requirement: Generation is bounded by truncation

A generation SHALL emit nodes at most two levels below the primary root, at most 7 children per parent counted across calls, and at most 60 nodes in total. Children beyond a bound SHALL be dropped, not rejected. A call whose parent was dropped, or descends from a dropped node, SHALL be dropped silently. A call left with no children SHALL emit no op.

#### Scenario: Third level dropped

- **WHEN** the model adds children under a node two levels below the root
- **THEN** that call emits no op and the generation continues

#### Scenario: Per-parent overflow truncated

- **WHEN** the model gives the root 9 children across its calls
- **THEN** only the first 7 are emitted

#### Scenario: Children of a truncated node dropped

- **WHEN** the model's 8th root child `h` was dropped and the model then adds children under `h`
- **THEN** that call emits no op and the generation completes normally

#### Scenario: Total bound

- **WHEN** a generation's bounds are configured with a total of 5 and the model offers 8 nodes
- **THEN** only the first 5 nodes are emitted

### Requirement: Model turns are bounded and stop when the skeleton is complete

A provider attempt SHALL answer each turn's tool calls with acknowledgements and continue for at most 4 model turns. It SHALL end without requesting another turn when the model ends its turn naturally. It SHALL also end without requesting another turn when, at the end of a turn, every emitted first-level node has received at least one child. Each turn SHALL cap model output at 8000 tokens.

#### Scenario: Two-turn skeleton

- **WHEN** the model adds first-level children in turn 1 and children for each of them in turn 2
- **THEN** ops from both turns are emitted and no third turn is requested

#### Scenario: Turn limit

- **WHEN** the model keeps calling tools in every turn
- **THEN** no fifth turn is requested and the generation completes with the ops emitted so far

### Requirement: Failed attempts retry once only before the first op

A transport failure or invalid output SHALL trigger exactly one fresh attempt if no op has been emitted yet. A refusal SHALL never be retried. A failure after the first op SHALL end the generation with its error and no retry. Client-initiated aborts SHALL never retry. Provider SDK built-in retries SHALL be disabled.

#### Scenario: Retry succeeds

- **WHEN** the first attempt fails before emitting any op and the second attempt succeeds
- **THEN** the generation emits the second attempt's ops and completes

#### Scenario: Retry exhausted

- **WHEN** both attempts produce invalid output before any op
- **THEN** the generation ends with error code `invalid-output` after exactly two provider requests

#### Scenario: Failure after first op

- **WHEN** a transport failure happens after two ops were emitted
- **THEN** the generation ends with error code `provider-error`, the two ops stand, and no second attempt starts

#### Scenario: Refusal

- **WHEN** the model refuses before any op
- **THEN** the generation ends with error code `refused` after exactly one provider request

### Requirement: Generation has a total time limit

A generation SHALL end with error code `timeout` and abort its provider call 30 seconds after it started, if it has not ended earlier.

#### Scenario: Slow provider

- **WHEN** a provider has not finished 30 seconds after the request started
- **THEN** the provider call is aborted and the generation ends with `timeout`

### Requirement: Errors never leak provider detail or user input

Errors exposed beyond the server SHALL carry only an error code from `timeout`, `provider-error`, `invalid-output` or `refused`, with a fixed diagnostic message per code. They SHALL never contain provider response bodies, keys or the user's topic. Logs SHALL record each generation's provider, model, attempt count, op count, duration and outcome, and SHALL NOT contain the topic text or keys.

#### Scenario: Provider HTTP error body withheld

- **WHEN** the provider answers an HTTP error whose body contains the key and a request id
- **THEN** the surfaced error is `provider-error` with its fixed message, and no log entry contains the body, the key or the topic

### Requirement: Every adapter honours the same provider contract

The Claude, OpenAI-compatible and mock adapters SHALL each satisfy every requirement of this capability under the same tests. Real adapters SHALL send the same unified instruction, the same tool definition and the topic only in the user turn.

#### Scenario: Same contract for every adapter

- **WHEN** the shared provider contract tests run against each adapter with that adapter's wire fixtures
- **THEN** all three pass the same op-validity, fresh-id, turn-loop and abort checks

#### Scenario: Same instruction for real adapters

- **WHEN** the Claude and OpenAI-compatible adapters build their first request for the same topic
- **THEN** both carry the identical instruction text and tool schema, and the topic appears only in the user turn

### Requirement: Prompt states one unified contract

The unified instruction SHALL ask the model for the following:

- two levels below the root, 3–7 children per parent;
- each child at most 40 characters, without paragraphs;
- mutually exclusive siblings;
- output language following the topic;
- changes only through the tool, one parent per call, temporary ids with `root` for the primary root;
- the root call first, then every first-level call in one turn.

#### Scenario: Instruction content

- **WHEN** the instruction text is inspected
- **THEN** it states each constraint listed in this requirement

### Requirement: Mock provider is deterministic

The mock provider SHALL produce the same op sequence for the same topic. For an ordinary topic, that sequence SHALL be one op adding 4 first-level children followed by one op of 3 children under each, through the same validation and id replacement as real providers. The reserved topics `mock:error-after-2`, `mock:invalid-first` and `mock:refused` SHALL respectively fail with a transport error after two ops, produce invalid output on every attempt, and refuse.

#### Scenario: Deterministic skeleton

- **WHEN** the mock provider generates for topic `学习 TypeScript` twice
- **THEN** both runs emit 5 ops (16 nodes) with identical texts and structure, and different ids

#### Scenario: Scripted mid-stream error

- **WHEN** the mock provider generates for `mock:error-after-2`
- **THEN** exactly two ops (7 nodes) are emitted before a `provider-error`
