# Design

## Context

See proposal.md — Why. Constraints that shape the approach:

- `AGENTS.md` / `CONTEXT.md`: DDD strict — `src/contexts/map/domain` is pure (no framework imports, enforced by `pnpm boundaries`); `application/` orchestrates through ports and never imports `infrastructure/`; `src/app` is the composition root and nothing imports from it. Zustand is permitted only for the editor store, which dispatches `TreeOp`s (decision 0003).
- L4 gates: 90% per-file coverage, TDD pairing hook, 700-line files, complexity 10, Playwright e2e on key UI paths, no real-key AI calls (none here).
- Stage 1 grill ledger (13 user decisions, 4 assumptions, 2 open items) is binding; every decision below cites its branch.
- Existing home page (`src/app/page.tsx`, `data-testid="app-ready"`) is the e2e anchor for `/`; `/maps/[id]` is registered as pending in `constraints.yaml`.

## Goals / Non-Goals

**Goals**

- A usable mind-map editor with no AI: build, edit, reorganise, collapse, undo, persist locally, reopen (PRD M1 acceptance).
- A `TreeOp` reducer stable enough that M3+ providers only emit ops; no UI rewrite when AI arrives.
- Forest model with a primary root (grill Q4/Q5) without losing the "one map has one topic" product semantics.

**Non-Goals**

- Layout direction switch (TB / radial) — LR only; the layout module takes a direction parameter but no UI exposes it (grill Q3).
- Equal multi-root maps without a primary root (grill Q5 alternative).
- Free hex colors or a color picker — six semantic tokens only (grill Q11).
- Markdown rendering of notes — plain multi-line text (grill Q12).
- Persisting undo history across reloads (assumption 3).
- Deleting the primary root — it can be renamed and have its children cleared (assumption 1).
- Export (M6), AI generation/Grow (M3/M4), cloud sync/accounts (M2), touch/mobile editing, collaborative editing.
- Replacing `replace_children`'s UI — the op exists for AI; M1 exposes no UI for it.

## Decisions

### D1. Forest with primary root (grill Q4, Q5; supersedes single-root invariant)

`MindMap { id, title, roots: MindNode[], createdAt, updatedAt }` where `roots[0]` is the primary root (never deleted, laid out at the canvas origin) and `roots[1..]` are floating subtrees. A floating root carries `position: { x, y }` (canvas coordinates, user-placed); non-root nodes never carry `position`. `MindNode { id, text, note?, color?: ColorToken, collapsed?, position?, children }`.

Alternatives: keep single-root and model floating nodes as a special child kind (rejected — leaks a fake parent into layout and export); equal multi-root (rejected by user — every AI/export action would need a "which tree" prompt).

Consequences: decision record 0004 ships in this change; `CONTEXT.md` invariant "single-root aggregate" becomes "forest with one primary root"; `openspec/glossary.md` `MindMap` entry and `docs/TECH.md` §3 are revised in the same PR (grill Q6). The aggregate root for consistency purposes is the `MindMap`; a single op touches one `MindMap`.

### D2. TreeOp protocol v1 (extends TECH §4)

| op                  | payload                                                    | notes                                                                                                                                                           |
| ------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `add_children`      | `parentId`, `children: NewNode[]`, `index?`                | `NewNode = { id, text, note?, color? }`; ids are generated by the caller (`nanoid`) so the op is replayable                                                     |
| `add_root`          | `node: NewNode`, `position`                                | creates a floating root; never creates a primary root                                                                                                           |
| `update_node`       | `id`, `text?`, `note?`, `color?`, `collapsed?`             | partial update; `position` is not updatable here                                                                                                                |
| `delete_node`       | `id`                                                       | rejected for `roots[0]`; deletes the subtree                                                                                                                    |
| `move_node`         | `id`, `newParentId: NodeId \| null`, `index?`, `position?` | `null` detaches into a floating root at `position` (required when `null`); rejected when `newParentId` is `id` or a descendant of `id`; rejected for `roots[0]` |
| `set_root_position` | `id`, `position`                                           | floating roots only                                                                                                                                             |
| `replace_children`  | `parentId`, `children: MindNode[]`                         | retained for AI (M3+); no M1 UI                                                                                                                                 |

`applyOp(map, op): { map, inverse }` is a pure function in `domain/`; it throws a typed `TreeOpError` (`cycle`, `primary-root-protected`, `unknown-node`, `invalid-target`) instead of silently no-op-ing (AGENTS.md: misconfiguration fails loud). Every op has an exact inverse (e.g. `delete_node` → `add_children`/`add_root` with the removed subtree and index; `move_node` → `move_node` back with the original parent/index or `set_root_position`). Zod schemas for every op live beside the types so M3 provider output validation reuses them (Important Development Note 2).

Alternative: immutable snapshot history (zundo) — rejected: snapshots of a 500-node map per keystroke-level op cost memory, and inverse ops make "one op = one undo step" and AI-session grouping trivial. `docs/TECH.md` §2 drops the zundo mention.

### D3. Undo history as an inverse-op stack with explicit groups (grill Q2, Q8)

`History { past: Entry[], future: Entry[] }`, `Entry = { ops: TreeOp[], inverses: TreeOp[], label }`. `dispatch(op)` applies, pushes `{ops:[op], inverses:[inverse]}`, clears `future`. `beginGroup(label)` … `endGroup()` collapse all dispatches in between into one entry; multi-select delete / group reparent / color use it (grill Q9); M3 AI sessions reuse it (CONTEXT.md invariant). History is capped at 200 entries (oldest dropped). Text editing commits a single `update_node` on blur/Enter; Esc discards. History lives in the Zustand editor store, not in the persisted map.

### D4. Layout: d3-hierarchy `tree()` per root, LR by axis swap (grill Q3)

`layoutForest(map, { direction: 'LR', nodeSize, gap })` → `{ positions: Map<NodeId, {x,y}>, edges }`. Primary tree is laid out from origin; each floating subtree is laid out from its own `position`. Collapsed nodes contribute no descendants. Node dimensions are measured (`ResizeObserver`) and fed back as `nodeSize` per node; a first pass uses estimated width from text length so the first paint has no jump. The function is pure and lives in `application/layout/`, tested without React.

Alternative: ELK / dagre — rejected: heavier dependencies for a tree, and both struggle with per-root free positioning.

### D5. Canvas: React Flow as a controlled view, never the source of truth

`@xyflow/react` renders nodes/edges derived each render from `map + layout + selection`. React Flow's internal node state is overwritten from the store; drags are intercepted: `onNodeDragStop` runs a hit test against laid-out node rects — drop on a node → `move_node(newParentId)`, drop on empty canvas → `move_node(null, position)` (detach) or `set_root_position` when the dragged node is already a floating root. Multi-select drag moves the selected set as one group under the same target (one history group). Custom node component renders title, color token, collapse toggle, note indicator; inline editing swaps the title for an input.

Selection, editing state, context-menu state, pan/zoom live in the editor store's UI slice, never in the map.

### D6. Context menu as a registry (grill Q10)

`MenuItem { id, label, shortcut?, isEnabled(ctx), run(ctx) }` registered in `application/menu/`. M1 registers eight items: add child, add sibling, rename, delete, collapse/expand, set color (submenu of six tokens), edit note, detach to floating. M4 registers the four Grow actions without touching the menu component.

### D7. Persistence: IndexedDB via `idb`, repository port in domain (grill Q7)

`MapRepository { list(): Promise<MapSummary[]>; get(id); put(map); delete(id) }` defined in `domain/`; `IndexedDbMapRepository` in `infrastructure/persistence/` stores `{ schemaVersion: 1, map }` under key `id` in object store `maps`. Autosave: the editor store debounces `put` 500 ms after the last op; a pending save flushes on `beforeunload`. When IndexedDB is unavailable (private mode, blocked storage) the app falls back to an in-memory repository and shows a persistent "未保存到浏览器" banner — it never silently pretends to save. Tests use `fake-indexeddb`.

### D8. Routes (grill Q7)

`/` — map library (Server Component shell + client list): create (new map with primary root text "新导图"), open, rename, delete (confirm). `/maps/[id]` — editor; unknown id shows a not-found state with a link back. Both are client-rendered data paths; no API routes in M1.

### D9. Colors and text (grill Q11, Q12)

`ColorToken = 'red' | 'orange' | 'yellow' | 'green' | 'blue' | 'purple'`; the theme maps tokens to CSS variables (light/dark). Title is single-line, unbounded, Enter commits; note is a plain `textarea` in a side panel, autosaved via `update_node` on blur.

### D10. Keyboard (grill Q13)

Tab add child; Enter add sibling (on the primary root: add child); Delete/Backspace delete selection; F2 or double-click edit; Esc cancel edit / clear selection; Cmd/Ctrl+Z undo; Cmd/Ctrl+Shift+Z redo; arrow keys move selection (←→ parent/first child, ↑↓ previous/next sibling); Space+drag or middle-button pan; wheel zoom; Cmd/Ctrl+A select all. Shortcuts are inert while an input has focus.

## Sketch seams under test

- `applyOp` / `invert` in `src/contexts/map/domain` — the highest seam: every invariant (cycle, primary-root protection, inverse exactness) is provable with pure unit tests; already the place M3 validation will hook in.
- `layoutForest` in `application/layout` — pure, covers collapse and floating placement without rendering.
- `MapRepository` contract test run against `IndexedDbMapRepository` (fake-indexeddb) — the only persisted-state boundary.
- Playwright walk of `/` and `/maps/[id]` (create map → add child via Tab → rename → drag-reparent → reload → tree persists) — the single end-to-end path that proves M1 acceptance; UI interaction details are not unit-tested one by one.

## Risks / Trade-offs

- [500-node drag may drop frames with per-render layout recomputation] → memoise layout on `(map, collapsedSet)`; recompute only the affected root's subtree on `set_root_position`; measure before optimising further (open question 1).
- [React Flow drag semantics fight the tree model] → nodes are `draggable` but positions are reset from layout after every drag; hit test is ours, not React Flow's connection logic.
- [IndexedDB unavailable or quota errors] → in-memory fallback + banner (D7); `put` failures surface as a toast, never swallowed.
- [Forest change ripples into docs] → all document revisions ship in this change's PR set (decision 0004 first).
- [Inline editing vs shortcuts conflict] → one `isEditing` flag in the UI slice gates every shortcut.

## Migration Plan

- Greenfield: `schemaVersion: 1` is the first persisted shape; a reader that meets a higher version refuses to load and reports it.
- M2 cloud sync reads the same `{ schemaVersion, map }` envelope; no browser-side migration is planned for M1.
- Rollback: feature is additive; removing the routes leaves IndexedDB data inert.

## Open Questions

1. How the "500 节点拖拽不掉帧" target is verified — manual profiling note in the PR vs a Playwright timing assertion; does not change specs or tasks (decide when task 8.3 lands).
2. Snap/attach affordance when a floating subtree is dragged near the primary tree — drop-on-node only (current design) vs proximity snapping; a UX refinement that leaves the ops unchanged.

## Not yet specified

- Touch and mobile interaction model for the canvas (PRD lists mobile editing as out of v1 but a read-only mobile view is unresolved).
- Snapping/alignment helpers for floating subtrees (grid, guides) — the problem space is visible but no requirement can be stated yet.
